# 2차 MVP 계획

> 상태: 초안 · 작성일 2026-08-21

## 목표

수익화 기반을 마련한다. 구독으로 팔 만한 가치를 만들고, 그 가치를 뒷받침할 서버를 직접 구축한다.

## 1차 MVP에서 넘어온 전제

| 항목 | 현재 |
|---|---|
| 데이터 | SwiftData 로컬 전용 (App Group 컨테이너) |
| 네트워크 | 없음 (`pushType: nil`, 제3자 SDK 0개) |
| 계정 | 없음 |
| 수익화 | `ProManager.isPro`가 UserDefaults만 읽고 **사용처 0곳** — 껍데기 |
| Live Activity | **8시간 뒤 갱신 중단**, 앱을 열어야 정리됨 |

`ProManager`는 지금 죽은 코드다. 2차에서 실제 구독 상태와 연결한다.

## Pro 경계

| | 무료 | Pro |
|---|---|---|
| 메모 개수 | 제한 있음 (**개수 미정**) | 무제한 |
| Live Activity | 8시간 후 갱신 중단 | **무기한 유지** (push-to-start) |
| 기기 간 동기화 | 없음 | 있음 |
| 메모 타입 5종 | 전부 사용 가능 | 동일 |
| 검색·필터·접근성 | 전부 사용 가능 | 동일 |

**이미 제공하던 기능은 잠그지 않는다.** 1차 사용자가 쓰던 것을 유료화하면 반발을 산다. Pro는 *새로 생기는 가치*로만 구성한다.

가장 강력한 Pro 가치는 **LA 무기한 유지**다. 서버 비용이 실제로 드는 기능이라 과금 근거가 명확하고, 사용자가 매일 체감한다.

## 과금

- **구독 (월·연)**. 서버를 직접 운영하므로 지속 비용이 발생한다. 일회성 구매는 장기적으로 적자.
- StoreKit 2 사용. 외부 결제는 Apple 정책상 금지.
- 가격 **미정**.

## Apple 정책 제약

작업 전에 반드시 반영해야 하는 항목이다.

1. **소셜 로그인을 제공하면 Sign in with Apple이 필수** (App Store Review Guideline 4.8). Google·카카오만 넣고 Apple을 빼면 거절된다.
2. **디지털 기능 판매는 인앱결제만 허용**. 외부 결제 링크 금지.
3. **push-to-start**는 iOS 17.2+ 의 `Activity.pushToStartTokenUpdates` 사용. 앱이 종료된 상태에서도 서버가 새 Live Activity를 시작할 수 있는 유일한 경로다.
4. Live Activity 자체의 8시간 제약은 사라지지 않는다. **8시간마다 서버가 새로 띄우는 방식**으로 우회한다.

## 작업 범위

### 서버 (NestJS)

- 인증: Sign in with Apple 토큰 검증, 세션 발급
- 메모 동기화 API (충돌 해결 정책 필요)
- APNs 연동: push-to-start 토큰 저장, 8시간 주기 재게시 스케줄러
- App Store Server API로 구독 상태 검증 (영수증 위조 방지)
- 호스팅·DB **미정**

### iOS

- Sign in with Apple 로그인 흐름
- 동기화 계층 (로컬 SwiftData ↔ 서버)
- `pushToStartTokenUpdates` 수집·전송
- StoreKit 2 구독 구매·복원·상태 관찰
- `ProManager`를 실제 구독 상태와 연결
- 무료 티어 메모 개수 제한 + 페이월

## 단계

가치가 없으면 팔 수 없으므로, **팔 물건을 먼저 만들고 결제를 붙인다.**

| 단계 | 내용 | 산출 |
|---|---|---|
| **1** | 서버 골격 + Sign in with Apple | 계정 체계 |
| **2** | 메모 동기화 | Pro 가치 ① |
| **3** | StoreKit 2 구독 + 서버 영수증 검증 | 수익화 동작 |
| **4** | push-to-start 재게시 | Pro 가치 ② |
| **5** | 무료 티어 개수 제한 + 페이월 | 전환 경로 |

5단계는 로컬만으로 가능해 언제든 넣을 수 있지만, **팔 것이 갖춰지기 전에 제한부터 걸면 이탈만 만든다.** 마지막에 둔다.

## 결정이 필요한 항목

- [ ] 무료 메모 개수 제한 (3개? 5개? 10개?)
- [ ] 구독 가격 (월·연)
- [ ] Sign in with Apple 외 추가 로그인 제공 여부
- [ ] 동기화 충돌 해결 정책 (마지막 쓰기 우선? 병합?)
- [ ] 서버 호스팅·DB 선택
- [ ] 기존 로컬 메모를 계정에 어떻게 귀속시킬지 (로그인 시점 업로드?)
- [ ] 구독 해지 후 동작 (동기화 중단? 읽기 전용? 로컬 유지?)

## 위험

**서버 운영 비용이 수익보다 먼저 발생한다.** 구독자가 없어도 APNs 스케줄러와 DB는 계속 돌아간다. 초기 비용을 감당할 수 있는 구조인지 확인이 필요하다.

**동기화는 난이도가 높다.** 오프라인 편집, 충돌, 부분 실패까지 다루면 1차 MVP 전체보다 클 수 있다. 범위를 좁히는 것을 권한다 — 예: 단방향(백업 전용)으로 시작.

**push-to-start 재게시는 검증이 어렵다.** 8시간 주기 동작을 확인하려면 실기기에서 하루 단위 관찰이 필요하다.

**1차 MVP가 아직 실기기 검증을 거치지 않았다.** 2차에 들어가기 전에 TestFlight로 한 번 돌려보는 편이 안전하다.
